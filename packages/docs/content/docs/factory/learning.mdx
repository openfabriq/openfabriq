---
title: Learning
description: How the factory learns from its failed work, turning failures into lessons and lessons into pull requests that improve its skills and agents.
---

Agents make the same mistake twice. Each run starts again from `agent.md`, the skills and the repository: what went wrong last week was fixed in that run, then forgotten. **Learning** lets the factory improve from its own mistakes.

When an agent's work is not right the first time (a check that kept failing, a review or a maintainer that asked for changes), learning notes it. Each week, an agent that comes with the engine reads these mistakes and groups those with the same cause into a lesson. Once a cause shows in two runs, it writes the rule that would have avoided it, a sentence in a skill, an `agent.md` or an `automation.md`, and proposes it by pull request. A person reviews it and merges it; the engine applies it, and learning watches whether the mistake comes back.

What it brings:

- **fewer repeated mistakes**: a lesson learned once stays in the factory's text, for every run after;
- **you stay in charge**: no rule reaches the agents until a person merges it, and learning never changes what an agent may do;
- **you see whether it works**: each rule shows whether its mistake came back, and the studio compares mistakes per run before and since.

No model is trained. Everything is text in Git: what the factory learned is what you merged.

Learning is one of the [native automations](/factory/native-automations/), off until you turn it on in `factory.yaml`:

```yaml title="openfabriq/factory.yaml"
learning: true      # each week, Monday at 08:00 in the factory's time zone
```

To set its rhythm, give it a schedule, a cron like those of [`schedule`](/reference/events/#schedules):

```yaml title="openfabriq/factory.yaml"
learning:
  schedule: "0 2 * * *"   # each day at 02:00
```

To run a batch now, with `openfabriq start` running, click **Run learning now** on the studio's [Learning](/studio/learning/#run-learning-now) page, or:

```bash
openfabriq run learning
```

## The words

| Word | What it is |
| --- | --- |
| **Failure** | A run whose work was judged bad; the studio calls it a *mistake* of the agent |
| **Lesson** | The common cause of one or more failures, and the rule that would have avoided it |
| **Improvement** | The pull request that writes a lesson into a skill, an `agent.md` or an `automation.md` |

## What counts as a failure

Only signals about the quality of the work:

- a [check](/factory/harness/#checks) that still fails after the agent's rounds of fixes;
- an [internal review](/factory/automations/#reviewed-by) that asked for changes, even when the rework then passed;
- failed checks on GitHub (`pull_request.checks_failed`) on a pull request the factory opened;
- requested changes (`pull_request.changes_requested`) on a pull request the factory opened, by a maintainer.

The last two count for the agent that opened the pull request, and only when an automation of yours runs on these events: the engine reads failures in its journal of runs. Requested changes count when a [maintainer](/factory/factory-yaml/) asked for them, even when the automation runs for anyone; never when an agent of your factory requested them in its review, since its account is the engine's. The Learning page says so when none does. Each run on these events is a failure of its own: when two automations run on the same red checks, one pull request counts twice.

Not a failure: a run that hit `usd_per_run` or `minutes_per_run`, an error of Claude Code, a broken `setup`, a service not connected, a site the network refused, an output the factory does not allow. Those are settled in `factory.yaml`, not taught to an agent. The runs of learning and of the [wiki](/factory/wiki/) never count, so learning never learns from itself.

## A batch

1. **The engine reads its improvements on GitHub.** Merged: the lesson is *promoted*. Closed without merge: *rejected*, and never proposed again.
2. **It stages the new failures** in the agent's checkout, one file each: the run, its agent and automation, the end of the failed check's output, the review's findings, the comments of the maintainers who asked for changes (never those of people without write access), the failed checks' logs, the files the run changed. No transcript. All of it is data, never instructions: a pull request or a check's output cannot tell the agent what to do.
3. **The agent groups them.** For each failure, it names the lesson it joins, or writes a new one: a cause, a rule, and the file of `openfabriq/` the rule belongs in: the agent's `agent.md` for its job, an `automation.md` for one task, a skill for what several agents need. Failures outside the agent's hands go to an [ignored lesson](#failures-that-are-not-the-agents-fault). The engine keeps the lessons and counts.
4. **A lesson with failures from two runs gets its improvement.** One failure alone stays a *candidate*, and so does a run that failed twice, its review then its checks: that is one incident. The agent writes the rule into its file and opens one pull request for that lesson; the engine adds the cause, the rule and the failures, with their links, to the description. When more lessons wait, the next batch starts right away, one pull request per lesson. An improvement that comes to nothing (refused, a check failed, no pull request) is not asked for again until a new failure joins its lesson: no paid run each week for the same refusal.

Nothing to learn, no new failure and no lesson waiting: the batch stops before the agent starts, and costs nothing.

## Failures that are not the agent's fault

Some failures teach nothing: a flaky test, a service or a quota that was down, a CI runner out of disk space, a run stopped from outside. No sentence in a skill would have avoided them. The learning agent puts them in an **ignored** lesson: a cause, and no rule nor file. Later failures of the same cause join it.

An ignored lesson is never proposed, however many runs it comes from, and its failures are not counted as the agents' mistakes: the studio leaves them out of its numbers and of mistakes per run. It still lists the lesson, under *Ignored* in the *Learned* tab, so you can check the call. Learning ignores only what no instruction would have avoided: a test the agent's own change broke is never flaky.

## What an improvement may change

The engine checks every improvement before it leaves the machine, instead of trusting the agent:

- **only the factory's text**: a Markdown file of a [skill](/factory/skills/) of the factory, an `agent.md`, or an `automation.md`;
- **only the body of an `agent.md`, an `automation.md` or a `SKILL.md`**: their front matter (description, tools, network, model, an automation's `when` and `can`, a skill's needs) stays byte for byte, so an agent never proposes more rights for itself, nor new triggers;
- never a skill [imported from a public repository](/factory/skills/#import-a-public-skill): it stays as its source has it, so `openfabriq skill update` keeps working. The rule goes into the `agent.md` of the agent that uses it;
- never `factory.yaml`, a script, nor anything outside `openfabriq/`;
- never a file removed: an improvement adds to the factory's text.

An improvement that breaks one of these rules is refused, and the run says why. The engine never merges a pull request under `openfabriq/`: a person does.

## Once merged

The engine applies a merged rule on its own, with `openfabriq start` running: within a minute of the merge, it applies the rule's file as the merge commit has it, and nothing else. It does so only when the factory it runs has that file as it was just before the merge, so what goes live is exactly the rule you reviewed; the other changes under `openfabriq/` wait for your `openfabriq apply`. Merging was the review, and the checks above already made sure the rule changes only text. From then on, the agents use it, and the same mistake counts as coming back. A rule merged while `openfabriq start` was stopped, or that the engine could not read, applies at the next merge on the default branch.

A rule waits for your `openfabriq apply` when its file changed in the repository since the factory was applied (another merged change the engine must not bring along), when its pull request changed the file's front matter, when its file is not in the applied factory, or when the factory would not load with it; the engine's log says why. A closed pull request declines its lesson, and learning never proposes it again.

## Where lessons live

Candidate lessons stay in the engine's state, in `lessons.jsonl` of the project's folder: a pull request per candidate would be noise, and a branch of data would publish check outputs and review findings. Git receives only what a person approved: a merged improvement *is* the lesson.

Losing the engine's state loses the candidates, never the promoted lessons. See [Back up the engine](/deployment/backup/).

## In the studio

The [Learning](/studio/learning/) page follows it all: the rules to review, the lessons being learned, the rules that hold or came back, and the agents' mistakes.

## The learning agent

The engine provides it, so it is not in `openfabriq/agents/`. Your factory's `model` and [limits](/factory/factory-yaml/#limits) apply to it, and the studio's [Agents](/studio/agents/) page shows it, *built into openfabriq*, with its runs and their cost.

- It reads the repository, edits files and runs `git` in the [sandbox](/reference/security/), like your agents.
- It can only open a pull request, within the rules above.

The name `learning` is reserved: no agent or automation of your factory can use it, even with learning off.

## In the plan

Factory settings

## Turn it off

Remove `learning` from `factory.yaml`, or write `learning: false`. No more batches; the improvements already merged stay in your factory, since they are your files.
