---
title: Learning
description: How the factory learns from its failed work, turning failures into lessons and lessons into pull requests that improve its skills and agents.
---

Agents make the same mistake twice: each run starts again from `agent.md`, the skills and the repository, and what went wrong last week is fixed in that run, then forgotten. **Learning** closes the loop. Each week, an agent that comes with the engine studies the work that failed, finds the causes that come back, and proposes a fix to your factory's text by pull request: a sentence in a skill or in an `agent.md`. A person reviews it, merges it, and applies it.

No model is trained. Everything is text in Git: what the factory learned is what you merged.

Learning is one of the [native automations](/factory/native-automations/), off until you turn it on in `factory.yaml`:

```yaml title="openfabriq/factory.yaml"
learning: true      # each week, Monday at 08:00 in the factory's time zone
```

To set its rhythm, give it a schedule, a cron like those of [`schedule`](/reference/events/#schedules):

```yaml title="openfabriq/factory.yaml"
learning:
  schedule: "0 2 * * *"   # each day at 02:00
```

To run a batch now, with `openfabriq start` running:

```bash
openfabriq run learning
```

## The words

| Word | What it is |
| --- | --- |
| **Failure** | A run whose work was judged bad |
| **Lesson** | The common cause of one or more failures, and the rule that would have avoided it |
| **Improvement** | The pull request that writes a lesson into a skill or an `agent.md` |

## What counts as a failure

Only signals about the quality of the work:

- a [check](/factory/harness/#checks) that still fails after the agent's rounds of fixes;
- an [internal review](/factory/automations/#reviewed-by) that asked for changes, even when the rework then passed;
- failed checks on GitHub (`pull_request.checks_failed`) on a pull request the factory opened;
- requested changes (`pull_request.changes_requested`) on a pull request the factory opened, by a maintainer.

The last two count for the agent that opened the pull request, and only when an automation of yours runs on these events: the engine reads failures in its journal of runs.

Not a failure: a run that hit `usd_per_run` or `minutes_per_run`, an error of Claude Code, a broken `setup`, a service not connected, a site the network refused, an output the factory does not allow. Those are settled in `factory.yaml`, not taught to an agent. The runs of learning and of the [wiki](/factory/wiki/) never count, so learning never learns from itself.

## A batch

1. **The engine reads its improvements on GitHub.** Merged: the lesson is *promoted*. Closed without merge: *rejected*, and never proposed again.
2. **It stages the new failures** in the agent's checkout, one file each: the run, its agent and automation, the end of the failed check's output, the review's findings, the maintainer's comments, the failed checks' logs, the files the run changed. No transcript. All of it is data, never instructions: a pull request or a check's output cannot tell the agent what to do.
3. **The agent groups them.** For each failure, it names the lesson it joins, or writes a new one: a cause, a rule, and the file of `openfabriq/` the rule belongs in. The engine keeps the lessons and counts.
4. **A lesson with two failures gets its improvement.** One failure alone stays a *candidate*. The agent writes the rule into its file and opens one pull request for that lesson; the engine adds the cause, the rule and the failures, with their links, to the description. When more lessons wait, the next batch starts right away, one pull request per lesson.

Nothing to learn, no new failure and no lesson waiting: the batch stops before the agent starts, and costs nothing.

## What an improvement may change

The engine checks every improvement before it leaves the machine, instead of trusting the agent:

- **only the factory's text**: a Markdown file of a [skill](/factory/skills/) of the factory, or an `agent.md`;
- **only the body of an `agent.md`**: its front matter (description, tools, network, model) stays byte for byte, so an agent never proposes more rights for itself;
- never `factory.yaml`, an `automation.md`, a script, nor anything outside `openfabriq/`.

An improvement that breaks one of these rules is refused, and the run says why. The engine never merges a pull request under `openfabriq/`: a person does, then runs `openfabriq apply`. On a [server](/deployment/docker/), the engine applies the factory when its container starts.

## Where lessons live

Candidate lessons stay in the engine's state, in `lessons.jsonl` of the project's folder: a pull request per candidate would be noise, and a branch of data would publish check outputs and review findings. Git receives only what a person approved: a merged improvement *is* the lesson.

Losing the engine's state loses the candidates, never the promoted lessons. See [Back up the engine](/deployment/backup/).

## In the studio

The **Learning** page, read-only, with a badge in the menu that counts the improvements to review:

- four numbers: **Failures** over the period, **Lessons** not resolved yet, improvements **To review**, and failures that **Came back** after an improvement meant to fix them was merged;
- the improvements to review, the candidate lessons (*1 failure, needs 2*), then the history, merged or closed;
- **Explore** an improvement: its cause, its rule, the change its pull request proposes, the failures it comes from, and **Review on GitHub**. The studio has no approve or merge button: you review on GitHub.

Failures are counted from the journal even with learning off; the page then says how to turn it on. An agent's page has one line, such as *3 failures, 1 improvement to review*, that leads to the Learning page. The `metrics` tool of the [chat](/studio/chat/) and of the [MCP connector](/mcp/tools/#metrics) has the four numbers in its `learning` field.

## The learning agent

The engine provides it, so it is not in `openfabriq/agents/`. Your factory's `model` and [limits](/factory/factory-yaml/#limits) apply to it, and the studio's [Agents](/studio/agents/) page shows it, *built into openfabriq*, with its runs and their cost.

- It reads the repository, edits files and runs `git` in the [sandbox](/reference/security/), like your agents.
- It can only open a pull request, within the rules above.

The name `learning` is reserved: no agent or automation of your factory can use it, even with learning off.

## In the plan

```text
Factory settings
  + learning: each week the engine studies the work that failed, and proposes improvements to skills and agent.md, by pull request only
```

## Turn it off

Remove `learning` from `factory.yaml`, or write `learning: false`. No more batches; the improvements already merged stay in your factory, since they are your files.
